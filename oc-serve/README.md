# oc-serve — `opencode serve` как задача Планировщика (Windows)

Сервер opencode на этой машине поднимается не в терминале, а задачей Планировщика
в **фоновой S4U-сессии**: окна нет, вход в систему не нужен, сервер живёт после
закрытия всех терминалов и переживает перезагрузку.

## Состав

| Файл | Что это |
|---|---|
| `oc-serve-task.sh` | лаунчер: берёт окружение из `~/.bashrc` и запускает алиас `oc-serve`; пишет лог, следит за флагом остановки, диагностирует падения |
| `oc-serve-common.sh` | общие помощники (только `source`): состояние, порт из алиаса, проверка порта, ротация лога |
| `oc-serve-stop.sh` | остановка сервера из bash/ssh: ставит флаг и ждёт освобождения порта (тот же контракт, что у `.cmd`) |
| `oc-serve-stop.cmd` | то же самое, но для Windows-консоли |
| `register-task.ps1` | установка/перерегистрация задачи (нужен админ, разово) |
| `verify.ps1` | проверка состояния: задача, порт, сессия, watchdog, флаги, HTTP |
| `opencode-serve.task.xml` | снимок определения задачи (экспорт Планировщика) |
| `tests/` | функциональные тесты: лаунчер, стоп, ротация, диагностика (в песочнице) |

Разворачивается в:

```
%USERPROFILE%\.local\bin\oc-serve-task.sh        ← лаунчер
%USERPROFILE%\.local\bin\oc-serve-common.sh      ← общие помощники (source)
%USERPROFILE%\.local\bin\oc-serve-stop.cmd       ← стоп (Windows-консоль)
%USERPROFILE%\.local\bin\oc-serve-stop.sh        ← стоп (bash/ssh)
%USERPROFILE%\.local\state\oc-serve\serve.log    ← лог (stdout+stderr сервера)
%USERPROFILE%\.local\state\oc-serve\serve.log.1  ← предыдущий лог (одна копия)
%USERPROFILE%\.local\state\oc-serve\serve.err    ← stderr оболочки-обёртки задачи
%USERPROFILE%\.local\state\oc-serve\stop          ← флаг остановки (появляется на время)
%USERPROFILE%\.local\state\oc-serve\.oc-serve-task.<pid>.sh  ← приватная копия лаунчера
```

## Установка

```powershell
Start-Process powershell -Verb RunAs -ArgumentList '-NoProfile','-ExecutionPolicy','Bypass','-File',"$PWD\register-task.ps1"
```

Скрипт разложит лаунчер, общий файл и оба стоп-хелпера в `%USERPROFILE%\.local\bin`
и перерегистрирует задачу `opencode-serve` (idempotent, `-Force`). Параметры:
`-TaskName`, `-WorkingDirectory`, `-BashPath`, `-InstallDir`, `-User`. Снести:
`.\register-task.ps1 -Unregister`.

> **Из ssh регистрация требует `-User`.** Через ssh `$env:USERDOMAIN` = `WORKGROUP`
> (это не домен), и S4U-регистрация падала с `HRESULT 0x80070534` — «нет
> сопоставления имени и SID». Поэтому `register-task.ps1` сам подставляет
> `$env:COMPUTERNAME`, когда `USERDOMAIN` пуст или равен `WORKGROUP`
> (получается `VETYMAE\oqyude` — тот же SID, что у работающей задачи:
> `S-1-5-21-2551243831-3760563278-1823068461-1003`). Если имя нужно задать
> руками: `.\register-task.ps1 -User "$env:COMPUTERNAME\$env:USERNAME"`.
> Имя дополнительно проверяется на сопоставление с SID — ошибка в имени
> теперь читаемая, а не `0x80070534` из Планировщика.

Определение задачи:

| | |
|---|---|
| Пользователь | `<домен>\<пользователь>`, `LogonType=S4U`, `RunLevel=LeastPrivilege` |
| Триггеры | при загрузке (+20 с), при входе пользователя |
| Действие | `"C:\Program Files\Git\bin\bash.exe" -c "exec …/oc-serve-task.sh"` |
| Рабочий каталог | `S:\Git` |
| Лимит времени | нет (`PT0S`) |
| Параллельные запуски | `IgnoreNew` |
| При сбое | перезапуск раз в минуту, до 999 раз |
| Батарея/простой | не останавливать |

## Как работает

```
Task Scheduler (S4U, session 0)
└─ bash -c "exec oc-serve-task.sh"            ← engine-процесс задачи
   └─ bash .oc-serve-task.<pid>.sh             ← приватная копия лаунчера (exec)
      ├─ opencode.exe serve …                 ← сам сервер (child, $child)
      └─ watchdog: while sleep 2; …           ← ждёт файл stop
```

1. Лаунчер делает `exec >>serve.log 2>&1` — консоли нет, поэтому весь вывод в лог.
2. `source ~/.bashrc` — источник `OPENCODE_SERVER_PASSWORD`, PATH для scoop-версий,
   `OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS` и т.д.
3. Команда не дублируется: берётся алиас `oc-serve` из `~/.bashrc`
   (`opencode serve --hostname 0.0.0.0 --port 4096 --cors https://<host>.opencodes.zeroq.su`),
   порт для проверки занятости тоже вычитывается из него.
4. **Приватная копия.** Лаунчер сначала копирует себя в
   `$LOG_DIR/.oc-serve-task.<pid>.sh` и продолжает уже из неё (`exec bash …`).
   Причина — см. «Что было поломано»: bash перечитывает файл скрипта по ходу
   работы, и перезапись лаунчера на лету ломает работающий экземпляр.
5. **Ротация лога.** Если `serve.log` больше `OC_SERVE_LOG_MAX_KB` (по умолчанию
   512 КБ), он сдвигается в `serve.log.1` (одна копия, без цепочки) — до первого
   `exec >>`, иначе файл уже открыт и не сдвигается.
6. **Диагностика.** В лог пишется, что запускается (`--- command:`), чем
   (`--- binary :` → `command -v`) и из какого PATH (`--- PATH   :`). Если
   бинаря нет в PATH, лаунчер не запускает мусор, а пишет
   `!! opencode не найден в PATH, PATH=…` и выходит с `rc=127`.
7. **Guard:** если `127.0.0.1:<port>` уже слушается — пишет в лог и выходит `rc=0`,
   чтобы не воевать с ручным запуском и не уходить в цикл перезапусков.
8. Сервер стартует дочерним процессом, лаунчер сидит в `wait`, watchdog раз в 2 с
   проверяет флаг `stop` и заодно замечает, если файл лаунчера переписали на лету.

## Остановка и запуск

```powershell
schtasks /run /tn opencode-serve                  # запустить
C:\Users\<user>\.local\bin\oc-serve-stop.cmd      # остановить (Windows-консоль)
```

Из bash/ssh — тем же флагом, но без PowerShell:

```bash
~/.local/bin/oc-serve-stop.sh                    # из ssh или из Git Bash
```

`oc-serve-stop.sh` и `oc-serve-stop.cmd` делают одно и то же: создают флаг
`$LOG_DIR/stop`, ждут освобождения порта до 20 с, `exit 0` — сервер остановился,
`exit 1` — порт всё ещё слушается (смотри лог). Порт берётся из того же места,
что и в лаунчере, — из алиаса `oc-serve` в `~/.bashrc` (общий код в
`oc-serve-common.sh`); если алиас недоступен — `$OC_SERVE_PORT`, иначе 4096.

**`schtasks /end` сервер не останавливает.** Проверено на этой машине: Планировщик
рапортует `SUCCESS` и переводит задачу в `Ready`, но дерево процессов (bash + сервер)
остаётся жить; `Stop-Process` из обычной сессии получает `Access denied`, потому что
процессы находятся в другой логон-сессии (S4U). Отсюда флаг + watchdog: лаунчер сам
гасит сервер и выходит **с кодом 0**, задача уходит в `Ready`, политика
«перезапуск при сбое» не срабатывает (она остаётся только для настоящих падений).
Флаг удаляется при старте, поэтому старый запрос не убивает новый сервер.

## Проверка

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\verify.ps1 -PublicUrl https://<host>.opencodes.zeroq.su/
```

Что смотрит: задача существует/запущена/`S4U`, порт слушается, сервер в сессии 0,
родитель — лаунчер `oc-serve-task*` (после перехода на приватную копию это
`.oc-serve-task.<pid>.sh`), watchdog перезапускает `sleep` (значит цикл живой),
нет висящих флагов, локальный и публичный HTTP отвечают 200.

Функциональные тесты (в песочнице, реальный сервер и `$HOME` не трогают):

```bash
bash oc-serve/tests/run-tests.sh          # Linux/macOS: 19 проверок
bash oc-serve/tests/run-tests-win.sh      # Windows/Git Bash: 16 проверок
pwsh -NoProfile -File oc-serve/tests/test-register-user.ps1   # Resolve-User: 7 проверок
```

Тесты закрывают: старт и диагностику в логе, «порт занят» → `rc=0`, остановку
через `oc-serve-stop.sh`, «бинаря нет в PATH» → `rc=127` с внятным сообщением,
ротацию лога на синтетическом файле > лимита, и главное — что перезапись файла
лаунчера на лету больше не убивает работающий экземпляр.

Отдельно (группы 7 / W7) идёт **не-проверка**: тот же сценарий на лаунчере до
приватной копии (`tests/fixtures/oc-serve-task.pre-private-copy.sh` — побайтовая
копия версии из `df07f47`). Она только печатает, воспроизвёлся инцидент или нет,
и ничего не засчитывает: результат зависит от того, как именно эта версия bash
перечитывает изменённый файл, — на другой машине он может не воспроизвестись.
Разбор инцидента — в следующем разделе.

## Что было поломано

### 1. `rc=127` при первом запуске — это был не «command not found»

На хосте в `serve.log` осталось:

```
=== 2026-10-29T13:41:14+0300 start pid=1597 … ===
--- alias oc-serve='opencode serve --hostname 0.0.0.0 --port 4096 …'
--- server pid=1610
server listening on http://0.0.0.0:4096
… INFO spawning process …            ← сервер ЖИВ, работает 7 минут
=== 2026-10-29T13:48:00+0300 exit rc=127 ===
```

Сервер к этому моменту был запущен и слушал порт, значит `opencode` в PATH был и
«не найден в PATH» к падению отношения не имело. Настоящая причина — **перезапись
файла лаунчера на лету**:

* `~/.local/bin/oc-serve-task.sh` перезаписан в **13:47:04** (установка новой
  версии), а экземпляр, стартовавший в **13:41:14**, умер в **13:48:00** —
  падение попадает в окно между перезаписью и смертью;
* раньше в том же логе есть прямая улика:
  `/c/Users/oqyude/.local/bin/oc-serve-task.sh: line 46: syntax error near
  unexpected token 'then'` (13:30:58) — bash читал **уже изменённый** файл
  (в обрывке — `2>&1` из старой версии, а не `2>/dev/null` из новой);
* снимок определения задачи перезаписан в **13:47:50** — значит `register-task.ps1`
  прогоняли в этот момент (перерегистрация задачи). Работавший сервер при этом
  исчез без единой строчки в логе, лаунчер «проснулся» после `wait`, перечитал
  подменённый файл и выполнил мусор: `command not found` → `rc=127`.

Механика: bash читает скрипт по мере выполнения (файл открыт и перечитывается),
поэтому подмена содержимого на диске превращается в мусорные команды.

Воспроизведено на живом хосте (vetymae, Git Bash) — старый лаунчер, файл которого
перезаписали, пока он ждал сервер:

```
deployed.sh: line 57: syntax error near unexpected token `then'
```

и то же самое на Linux (`line 87: ----------: command not found`). Новый лаунчер в
той же ситуации выживает и пишет в лог:

```
!! файл лаунчера /…/oc-serve-task.sh изменился во время работы — это обновление поверх работающего экземпляра
```

Что сделано:

* лаунчер стартует **с приватной копии себя** — перезапись оригинала больше никого
  не ломает (проверено: 19/19 локальных тестов, 16/16 на Windows — плюс
  информационная группа, которая воспроизводит инцидент на старом лаунчере);
* лаунчер **замечает** подмену файла (размер + mtime с наносекундами) и пишет
  об этом в лог — и предупреждение, идёт ли watchdog, и итоговая проверка при выходе;
* в лог всегда пишется окружение запуска (`command`, `binary → command -v`, `PATH`),
  а при ненулевом коде возврата — блок диагностики: код, бинарь, PATH, состояние
  порта. Если бинаря нет в PATH — `!! opencode не найден в PATH, PATH=…` и `rc=127`
  (тот же код, что и раньше, но теперь с объяснением).

> После установки нового лаунчера **перезапустите задачу**: старый экземпляр,
> начатый до обновления, приватной копии не имеет и подмену файла переживёт плохо.
> `register-task.ps1` предупредит об этом, если задача сейчас `Running`.

### 2. Ротация `serve.log`

Лог рос без предела (у соседнего директора `state/loop.log` однажды вырос до
15 МБ на спаме). Теперь при старте лаунчер, если `serve.log` больше
`OC_SERVE_LOG_MAX_KB` (по умолчанию 512), сдвигает его в `serve.log.1` — одна
копия, без цепочки. Сдвиг делается **до** первого `exec >>` (после открытия файла
на запись сдвинуть его нельзя, особенно на Windows, где файл держит открытым сам
сервер). Если сдвиг не удался (файл занят) — лаунчер пишет об этом в лог и
продолжает работу.

### 3. Регистрация из ssh

`$env:USERDOMAIN` через ssh = `WORKGROUP` → `HRESULT 0x80070534`. Исправлено
(см. «Установка»): fallback на `$env:COMPUTERNAME` + параметр `-User` + проверка
сопоставления с SID.

### 4. Остановка из ssh

`oc-serve-stop.cmd` работает только в Windows-консоли, из ssh приходилось звать
`powershell`. Добавлен `oc-serve-stop.sh` — тот же контракт, рядом с лаунчером,
порт берётся из того же алиаса (код не дублируется — общий `oc-serve-common.sh`).

## Грабли

- **Регистрация требует админа.** Создать задачу с `LogonType=S4U` из обычного
  процесса Windows не даёт (`Access denied`). Это про создание, а не про выполнение:
  сама задача работает с отфильтрованным (не повышенным) токеном —
  в `<Principals>` нет `<RunLevel>`, т.е. `LeastPrivilege`.
  Управление (`/run`, `/change /disable|/enable`) работает и без админа.
- **Не перезаписывайте `~/.local/bin/oc-serve-task.sh`, пока задача работает.**
  Bash перечитывает файл скрипта на лету — работающий экземпляр начнёт выполнять
  мусор (`syntax error`, `command not found`, `rc=127`). Новый лаунчер этому
  неуязвим (работает из приватной копии), но обновление всё равно стоит делать
  через остановку задачи.
- **`LastTaskResult = 0x800710E0`** — «запрос отклонён»: кто-то сделал `/run`,
  когда задача уже выполнялась (`IgnoreNew`). Безвредно.
- **`already listening` в логе** — порт занят другим экземпляром; лаунчер вышел
  `rc=0`. Остановите лишний и запустите задачу снова.
- **Сервер держит порт, а задача `Ready`** — значит экземпляр запущен лаунчером
  старой версии (без watchdog): снимите его elevated-`Stop-Process` или перезагрузкой.
- Логи сервера и лаунчера — в одном файле `serve.log`; строки лаунчера начинаются
  с `===` и `---`.
- **`.ps1` сохранены в UTF-8 с BOM.** Без BOM `powershell.exe` (5.1) читает файл как
  ANSI и падает с `Missing closing '}'` на кириллице. При правке файлов BOM сохраняйте.
- Для перенаправленного вывода скрипты сами переключают stdout на UTF-8; в старом
  консольном окне с cp866 читать такой файл нужно как UTF-8 (`chcp 65001` или редактор).
- На Windows порт держится и после смерти процесса (TIME_WAIT), поэтому «порт
  слушается» проверяется connect'ом, а не `netstat`.
