# Куда должны жить симлинк-скрипты: winos или powerlinks

**Дата:** 2026-10-13
**Вопрос:** архитектурно, где лучше держать симлинк-часть — в `S:\Git\winos` или в `S:\Git\powerlinks`?
**Контекст:** пользователь рассматривает перенос всех модулей «поверх идейной архитектуры winos», но решил не делать этого сейчас из-за высокого риска ошибки. Нужен ответ для прочтения позже.

---

## Короткий ответ

**Симлинк-движок должен остаться в `powerlinks`. Из `winos` стоит брать только оболочку — меню и диспетчер, но не сам движок.**

Это не вопрос вкуса. Два из трёх различий ниже — не стилистические, а функциональные: часть winos на этой задаче не работает, часть работает неправильно.

---

## 1. Тип ссылки — это не стилистика, это работоспособность

| | Junction | SymbolicLink |
|---|---|---|
| `powerlinks` | динамически, для каталогов | только для файлов |
| `winos` | **0 вхождений во всём `src/`** | 4× жёстко, без вариантов |

Счётчик по исходникам:

```
winos      ItemType SymbolicLink: 4    ItemType Junction: 0
powerlinks ItemType SymbolicLink: 0*   ItemType Junction:  2
```
\* в powerlinks литерала нет — тип вычисляется в переменную `$linkType` (`src/modules/common/State.ps1:248-255`):

```powershell
$linkType = if (Test-Path -LiteralPath $sub.from -PathType Container) {
    'Junction'      # каталог — без прав админа
} else {
    'SymbolicLink'  # файл
}
New-Item -ItemType $linkType -Path $sub.to -Value $sub.from -Force
```

**Почему это решает задачу.** `New-Item -ItemType SymbolicLink` на Windows требует либо повышенных прав, либо включённого Developer Mode. Junction не требует ничего.

Все ссылки на аудио-плагины ведут в **каталоги** (`VSTPlugins`, `VST3`, `ProgramData`, `Documents`). Значит симлинковая реализация winos на этой задаче не запустится без повышения прав.

У winos это работало, потому что его цели — конфиги приложений и темы курсора, и он запускался из-под админа. Задачи разные, требования к привилегиям разные. Это не дефект winos — это несоответствие его решения нашей задаче.

## 2. Проверка источника перед созданием ссылки

**powerlinks** — `src/modules/common/State.ps1:228-240` и `:281`:

```powershell
if (-not (Test-Path -LiteralPath $sub.from)) {
    # Junction и SymbolicLink оба принимают несуществующую цель, поэтому
    # опечатка в манифесте иначе разбросала бы по системе битые ссылки,
    # и это всплыло бы только когда DAW не сможет загрузить плагин.
    status = 'failed'
    note   = 'source does not exist'
}
```

**winos** — `grep` по `does not exist` не находит ничего, создаёт вслепую (`src/modules/common/State.ps1:238-245`):

```powershell

    if ($PSCmdlet.ShouldProcess($sub.to, "Create symlink to $($sub.from)")) {
        try {
            New-Item -ItemType SymbolicLink -Path $sub.to -Value $sub.from -Force ...
```

**Это ровно тот дефект, который был найден и починен в powerlinks в этой сессии** («`apply` создавал ссылки в никуда — Junction принимает несуществующую цель»). В winos он остаётся: опечатка в конфиге даст битую ссылку, которая всплывёт только когда DAW не сможет загрузить плагин.

## 3. Покрытие глаголов

| winos (3) | powerlinks (7) |
|---|---|
| `plan`, `apply`, `snapshot` | `plan`, `apply`, `revert`, `snapshot`, `status`, `adopt`, `verify` |

(`winos/src/modules/symlink-manager.ps1:3`, `powerlinks/src/modules/plugin-manager.ps1:3-4`)

Отсутствует в winos:

- **`revert`** — снять все junction'ы (откат)
- **`verify`** — read-only pre-flight перед применением
- **`status`** — детекция дрифта от последнего snapshot
- **`adopt`** — построить состояние из живой системы

---

## 4. Модель состояния и покрытие задачи

| | winos | powerlinks |
|---|---|---|
| Источник истины | плоский `data/data.json` | allowlist + 28 манифестов |
| Не-симлинковое поведение вендора | не моделируется | `Registry`, `Copy`, `Process` в манифесте |
| Песочница | **слово `sandbox` не встречается в `src/` ни разу** | полная, проверена циклом на 198 ссылках |
| Тесты симлинк-части | 16 (`state.Tests.ps1`) | 139 по всему проекту |
| Строк в слое состояния | `State.ps1` 468 | `State.ps1` 571 |

Манифесты — принципиальное различие. powerlinks фиксирует, что вендор делает **помимо** симлинков: импорт `.reg`, копирование деревьев, kill-скрипты перед откатом. У winos эквивалента нет — там только ссылки.

Песочница дала всё: по ней были найдены дефект `/MIR` и регрессия `@($null).Count = 1`. Без неё эти вещи вышли бы на живую систему.

## 6. Про идею «всё поверх архитектуры winos»

**Направление стоит перевернуть.** Если консолидация будет, переносить нужно **powerlinks в winos**, а не наоборот.

Причина: симлинк-слой winos всё равно придётся переписывать на junction-основу (§1), добавлять недостающие глаголы (§3) и защиту от битых ссылок (§2). То есть при консолидации всё равно тащится большая часть того, что уже написано здесь.

То есть консолидация — не перенос готового, а слияние двух независимых наборов дефектов: у каждого свои. Сначала довести каждый до ума по отдельности, потом решать.

**Согласен, что сейчас за это браться не стоит.** Оценка риска верная.

## 7. Оговорка

Сравнивалась **только симлинк-часть**. У winos есть ещё:

- `essentials` — темы курсора (69 строк)
- `opencode-serve` — менеджер служб (130 строк)

Это другие домены, они не разбирались. Если речь об **общей оболочке для всей системы** (а не только о симлинках), вопрос нужно обсуждать отдельно — возможно, там идея общей архитектуры имеет смысл.
